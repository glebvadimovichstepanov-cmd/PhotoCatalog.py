# Правила сохранности и восстановления

## Копирование

1. Проверяются границы source/destination и отсутствие symlink/junction.
2. Читаются метаданные; при их отсутствии используется mtime с объяснением причины. Отсутствующий файл — ошибка, текущее время не подставляется.
3. Формируется имя по дате и исходному имени. Для длинного имени сохраняется короткий идентификатор.
4. Вычисляется SHA-256 исходника и фиксируются размер, mtime, ctime и идентификатор файла.
5. Создаётся уникальный временный файл в целевой папке. Копия сбрасывается через fsync и проверяется по SHA-256. Исходник повторно проверяется на изменения.
6. mtime копии сохраняется. Права/ACL исходника не клонируются: результат наследует права целевой папки.
7. Windows rename публикует результат без замены; при гонке проверка занятого имени повторяется. На POSIX используется hard link без замены. Программа не использует os.replace для медиа.
8. Совпадение SHA-256 с неизменившимся существующим кандидатом означает duplicate. Разное содержимое требует другого имени. Сравнение выполняется в группе имён этого файла, а не глобально по каталогу.
9. При обычном исключении удаляется только собственный временный файл; существующие файлы не удаляются.

Защита распространяется на конкурирующие экземпляры приложения. Каталоги не должны одновременно модифицироваться сторонними программами: проверки ссылок и статуса не являются защитой от злоумышленника, который подменяет дерево между системными вызовами. Файлы не блокируются от внешнего редактирования на всё время работы.

После Ctrl+C уже опубликованные копии сохраняются. Пул может дождаться текущей пачки; нативный разбор одного медиафайла нельзя немедленно прервать потоком. Повторный запуск проверяет существующие результаты и продолжает работу.

После аварийного завершения процесса или выключения питания могут остаться .photocatalog-*.tmp и временные каталоги распаковки. Программа не удаляет их автоматически, чтобы не затронуть работу другого экземпляра. Удалять их следует только после проверки отсутствия работающих экземпляров; окончательные медиафайлы имеют обычные имена. fsync и атомарная публикация не дают абсолютной гарантии при аппаратном отказе, особенно на сетевых файловых системах. Проверенный сценарий — локальный Windows-диск.

## ZIP

Архив сначала проверяется целиком по именам и заявленным размерам. Запрещены абсолютные пути, .., обратные слеши, NUL/ADS, зарезервированные Windows-имена, ссылки, повторяющиеся имена без учёта регистра и зашифрованные элементы.

Каждый архив распаковывается в отдельный закрываемый временный каталог. Ограничиваются число элементов, общий заявленный и фактический объём, степень сжатия. zipfile проверяет CRC при чтении. При ошибке распаковки никакие медиа из частичного архива не передаются на копирование; остальные источники продолжают обрабатываться. Вложенные ZIP автоматически не раскрываются.

Лимиты применяются к одному архиву. Архивы обрабатываются последовательно; для одной распаковки нужно свободное место в TEMP, а для копии — на целевом томе. Чтение центрального каталога ZIP выполняется стандартной zipfile до проверки числа элементов: отдельного лимита RAM на ZIP-заголовки нет.

## Даты и dry-run

EXIF: DateTimeOriginal, DateTimeDigitized, DateTime. Видео: recorded_date, encoded_date, tagged_date, file_created_date. Невалидный кандидат не мешает проверить следующий. Дробные секунды и явные ISO/EXIF-смещения сохраняются. Наивная дата не получает выдуманный пояс; mtime интерпретируется в локальном времени компьютера. Каталог строится по записанному времени, без автоматического перевода в UTC.

Dry-run читает исходники и метаданные обычных файлов, но не создаёт каталог назначения, временные файлы или отчёт. Для ZIP используются только имена, заголовки и даты элементов; внутренние EXIF/видео и CRC не проверяются. Такой план помечен provisional и может отличаться от фактической сортировки. Занятые имена в плане обычных файлов отмечаются; окончательное имя/дубликат устанавливается при проверенном копировании. План не является резервированием имён.

ОС может сама обновлять время доступа при чтении; запрет записи в dry-run относится к операциям приложения, а не к системному учёту доступа или кешам ОС.

## Журнал

Логи предупреждений и ошибок выводятся в stderr. Полный JSON-отчёт содержит локальные пути, поэтому перед передачей третьим лицам его следует просмотреть. Сбой записи отчёта возвращает код 1, но не откатывает уже сохранённые медиа.

Один отчёт хранится в памяти до завершения. Пачки ограничивают одновременно отправленные задачи, но не объём итогового списка результатов. Для многомиллионной коллекции следующим улучшением может быть потоковый JSONL-журнал.
